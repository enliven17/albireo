# Ingress Skeleton Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans inline, with test-first domain changes and one final fresh review. Steps use checkboxes for execution tracking.

**Goal:** Complete roadmap step 4, then improve developer documentation and stop.

**Architecture:** Two independent Fastify instances/listeners in one process. No data acceptance, authentication, database or broker connections. Liveness succeeds; readiness and registered admission placeholders return 503 until their later implementation.

**Tech Stack:** Node 26.13.1 / 24.22.3, TypeScript 6.0.3, Fastify 5.12.8, TypeBox 1.4.7 and provider 6.3.0.

**Spec:** [Selected baseline](../2026-11-15-decisions.md), [roadmap step 4](2026-11-15-rollout.md), and the user's explicit request to stop feature work here and then improve documentation.

## Global Constraints

- Preserve legacy `/e`, tracker URLs, dashboard APIs and their current behavior.
- New service code gets strict indexed/optional checks, erasable syntax, typed lint and formatting. No experimental handlers imported.
- No 202 responses, fake durable receipts, database probes, queue publication or auth/session implementation.
- Defaults bind both listeners to loopback, on 8080/8081. Explicit private non-loopback binding requires deployment network isolation; a port name is not authentication.
- Conventional branch/commit names. Work in the existing managed worktree, with no push, merge or deployment.

## Review Focus

- Host/forwarded headers and encoded private paths cannot select the private instance from the public socket; exercise both injection and real listeners.
- Invalid configuration must fail before binding, with errors naming keys rather than reflecting values; tests include a secret-looking invalid value.
- Invalid/malformed/oversized/prototype-poisoning JSON, compressed bodies and framework errors produce bounded generic responses without input or secrets in logs.
- A second bind failure must close the first listener; shutdown must close both and tolerate repeated calls.
- Documentation must separate prototype behavior, the disabled new skeleton and planned production capabilities; commands and route/config tables must match tested behavior.
